# Releasing Passband

Write the release notes, push a tag; CI does the rest:

```sh
# 1. add an entry for the new version to the top of the table in
#    Sources/Passband/Lib/ReleaseNotes.swift
./make-changelog.sh          # regenerates ../docs/CHANGELOG.md from it
./test.sh                    # the release-notes suite checks the table

# 2. bump VERSION (and its project.yml mirror), commit, then:
git tag "passband-mac-$(cat VERSION)" && git push origin "passband-mac-$(cat VERSION)"

# a hotfix nobody should be pushed about: tag it quiet instead
git tag -a "passband-mac-$(cat VERSION)" -m quiet && git push origin "passband-mac-$(cat VERSION)"
```

## The release notes

`Sources/Passband/Lib/ReleaseNotes.swift` is the ONLY place a release note is
written. The app compiles that table directly and shows the unread part of it
in its What's New card on the first launch after an update, which is what makes
the notes a human reads impossible to leave stale. Everything else is generated
from it and should never be hand-edited:

| Output | Generated by |
| --- | --- |
| `docs/CHANGELOG.md` | `./make-changelog.sh` (CI fails on a stale one) |
| the GitHub release body | `./make-changelog.sh <version>`, called by the release workflow |

A version with no entry in the table still tags and still ships: the release
body falls back to the install line alone, and the card shows nothing. That is
deliberate, so a hotfix is never blocked on prose. It does mean a release worth
announcing needs its note written BEFORE the tag, since the app only ever shows
notes for versions it is at or past.

Notes are keyed by the MAC APP's version and say which surface each item landed
in: Mac, iPhone or daemon. The phone and the daemon each carry their own version
and tag (`passband-ios-X`, `daemon-X`, numbered on their own cadence), but their
user-facing changes ride in the Mac release that shipped alongside them: the
daemon has no screen of its own, and the phone reads its notes from the store.

House rules for the prose, enforced by the test suite where they can be: no em
dashes, say what the human can now do rather than what the commit did, and give
every item a surface.

`.github/workflows/release-passband-mac.yml` verifies the tag against both
`VERSION` and project.yml's macOS target, then builds, signs, notarizes,
publishes the GitHub release, regenerates the appcast (committed to main, which
redeploys the site), and bumps the Homebrew cask. It needs five repo
secrets, listed at the top of the workflow file. The daemon ships from
`daemon-*` tags and iOS from `passband-ios-*`; the three never overlap.

## Local fallback

The same release can be cut from this machine with one command:

```sh
./release.sh        # or --dry to rehearse without publishing
```

It runs the steps below, which are also what CI does — kept documented for
when a step needs doing by hand. Prerequisites on the release machine:
the Developer ID certificate, the `passband-notary` notarytool profile
(see build-release.sh), and the Sparkle EdDSA private key in the login
keychain (created by `vendor/Sparkle/bin/generate_keys`; back it up with
`generate_keys -x sparkle-private-key.txt` and store it somewhere safe —
whoever holds it can sign updates for every install).

1. Bump `VERSION` (and its mirror in project.yml), commit.
2. `./build-release.sh` — signs, notarizes, staples, leaves
   `build/Passband-$VERSION.zip`, and the binary's symbols beside it as
   `build/symbols-Passband-$VERSION.dSYM.zip`. The shipped binary is stripped,
   so that dSYM (same UUID, `dwarfdump --uuid`) is what symbolicates a crash
   report from this version. It goes on this repo's release only, never the
   public mirror, and is named so no `Passband-*.zip` glob takes it for an app
   archive.
3. Publish the archive under the `passband-mac-` tag (the daemon owns
   `daemon-*`, the phone owns `passband-ios-*`):

   ```sh
   gh release create "passband-mac-$(cat VERSION)" "build/Passband-$(cat VERSION).zip" \
     "build/symbols-Passband-$(cat VERSION).dSYM.zip" \
     --title "Passband $(cat VERSION)" --notes "..."
   ```

4. `./make-appcast.sh` — stages the zip into `releases/` and regenerates
   `../passband-site/appcast.xml` with a signed entry.
5. Commit and push `passband-site/appcast.xml` — the site redeploys and every
   install sees the update on its next check.

What an install then shows is Passband's own card, bottom centre of the window:
"Passband X.Y.Z is available" and one Update button that downloads, installs and
relaunches. Sparkle's own windows are not used (see Model/Updater.swift), so a
release with nothing but a version bump still reads correctly — that card never
shows release notes, and the appcast does not need to carry any.

The notes arrive AFTER the relaunch instead, from the table compiled into the
new build: the What's New card, once, on the first sync of the first session on
the new version (Model/WhatsNew.swift). Two cards, deliberately, because they
ask for different things. The update card interrupts you to request a restart;
the what's-new card is a thing to read once you are already running it.

The appcast enclosure points at `https://passband.app/download/<zip>`, which
the site 302s to the GitHub release asset, so the feed URL never depends on
where the archives are stored. `releases/` is the generator's working set:
keep it around so old entries survive regeneration; losing it only trims the
feed to the versions you re-stage.

## Release announcements (push)

A Mac where Passband is quit never sees the update card or banner, so the
daemons announce each release themselves (squelch-core/src/release_feed.rs).
Every daemon with a relay reads `passband.app/appcast.xml` hourly. Six hours
after a version appears there, it pushes it once to its account's Macs. Phones
are never told about a Mac release. An account whose Mac already connected on
the new version hears nothing. There is nothing to do per release: publishing
the appcast is the trigger.

A hotfix tagged `-m quiet` (above) is marked `<passband:quiet>` in the appcast
by `make-appcast.sh`: no daemon pushes it and a running Mac skips its banner,
but it installs like any other release. A quiet fix does not cancel a feature
release still inside its six hours; that push still goes, naming the newest
version. Decide at tag time: the mark comes from the tag message on every
regeneration, and once the six hours pass the push may already be out.

The Mac half needs the app to hold an APNs token, which needs a provisioning
profile. One-time setup, at developer.apple.com:

1. Identifiers > `app.passband.client` > tick **Push Notifications**, save.
2. Profiles > + > **Developer ID** (under Distribution) > App ID
   `app.passband.client` > the Developer ID Application certificate CI signs
   with > download the `.provisionprofile`.
3. `base64 -i Passband_Push.provisionprofile | gh secret set MAC_PUSH_PROFILE --env release-mac`
   (or as a repo secret, wherever the other release secrets live).

The relay already allow-lists `app.passband.client` as a topic, and its `.p8`
key is team-wide, so nothing changes on the server. Without the secret the app
ships exactly as before and never asks for a token. `build.sh` refuses to sign
with a profile for another app id or team, one without push, or an expired one,
because an app that claims push without a matching profile does not launch.
Profiles last a while but not forever: when it expires, the release fails with
a message saying so, and step 2 makes a new one.

Verify once on a real install: `codesign -d --entitlements - /Applications/Passband.app`
lists `com.apple.developer.aps-environment`, and after a launch the account's
daemon has a `macos` row in `devices`.
